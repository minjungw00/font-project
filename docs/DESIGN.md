# 설계 및 개발 단계

## 고정된 요구사항

Sarasa Fixed J 원본의 기존 CJK 윤곽 및 진행 폭을 유지한다. Pretendard/Harena식 확대는 하지 않는다. 영문과 CJK의 진행 폭 비율은 1:2, 추가 아이콘은 1셀을 목표로 한다. 일본식 기본 한자 자형, 코딩 리가처 제외 및 반각 em dash를 유지한다. Material Design 전체를 포함하는 Nerd Fonts 지원을 목표로 하되 문자 지원 범위를 희생하는 결정을 자동화하지 않는다.

## 초기 파이프라인

1. 버전과 SHA-256이 잠긴 원본 다운로드 및 검증.
2. 원본 Sarasa와 Symbols Nerd Font Mono의 cmap/maxp/hmtx를 분석한다. 추가 아이콘 개수와 여유 글리프 수는 추정치가 아니라 각각 실측하되, 합성 후 개수는 단순 합계와 다를 수 있다.
3. 공식 Nerd Fonts 패처를 --complete --single-width-glyphs --careful로 실행한다. --mono는 CJK 전각을 훼손할 수 있어 사용하지 않는다.
4. 임시 패밀리 이름을 OpenType name 테이블에 적용한다. 원본 라이선스 및 저작권 name 레코드를 보존한다.
5. 원본 코드포인트 및 IVS 매핑의 유무, 원본 진행 폭, 원본 UPM, 한글 11,172자, 반각·전각 샘플, 전체 MDI 및 PUA 아이콘, 실제 아이콘 수평 경계, 코딩 연산자 조판을 확인한다.
6. 검증 실패 시 build 명령을 실패 처리한다. 검사 통과 결과만 dist에 복사한다. dist 결과는 개발용이며 공개 릴리스가 아니다.

SymbolsOnly 배포판의 PUA 및 IEC power symbol 매핑은 기대 아이콘 집합의 기준이다. 기존 Unicode 비-PUA 문자가 충돌할 경우 원본을 우선한다. 패처의 모든 보조·비인코딩 글리프를 포함하는지를 이 검사만으로 증명할 수는 없다.

## 아직 결정하지 않은 것

- 글꼴 최종 이름과 코드 라이선스
- 원본 전체 지원 범위와 전체 아이콘을 동시에 수용하지 못할 경우의 글리프 절감 정책 (희귀 한자/IVS/중복 글리프 각각의 절감량을 먼저 조사)
- 아이콘 경계 검증 실패 시 도형 비율을 보존하는 수평 크기 조정 및 중앙 배치
- 최종 지원 굵기, 시각적 자간, 힌팅, 교차 플랫폼 테스트, 라이선스 번들
- 배포용 TTF 릴리스 자동화

## 검증 한계

메트릭 검사는 윤곽 보존 전체를 증명하지 않는다. 초기 검증은 코드 포인트, IVS 키, 진행 폭 및 아이콘의 glyf 경계를 확인하고 HarfBuzz로 대표 코딩 문자열을 확인한다. GSUB/GPOS 전체, IVS 실제 자형, 힌팅, 각 플랫폼 렌더링을 수동 테스트해야 한다. 글꼴의 내부 고정폭 메타데이터만으로 애플리케이션 호환성을 보장하지 않는다.

기존 한글·한자·가나는 삭제하지 않는 것이 기본 원칙이다. 용량을 초과하거나 폰트가 깨지면 조용히 생략하거나 자동 서브세팅하지 않는다.
